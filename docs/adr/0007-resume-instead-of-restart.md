# 0007 — Resume a failed run instead of restarting it

- **Status:** Accepted
- **Date:** 2026-08-25

## Context

A measured run exhausted its budget: **$8.18 over 82 turns**. It had completed
site capture, a design spec, `SCRIPT.md`, six voiceover takes, sound effects and
an 18 KB `STORYBOARD.md` — and had authored **zero frames**. It died exactly
where the expensive half begins.

Re-queueing from the prompt would have re-captured the site, re-generated the
voiceover and re-spent that budget on the work that had already succeeded.

## Decision

Re-queue **resumes by default**. A resumed job keeps its project directory, and
the agent receives an inventory of what is already on disk, generated by
`describeExisting()`, with instructions not to regenerate it:

```
- Script: `SCRIPT.md`
- Voiceover (6): `01.wav`, `02.wav`, …
- Captured screens (9): `full-page.png`, `scroll-000.png`, …
```

Decisions already answered are replayed too, so a resumed run is never asked the
same question twice. `--fresh` opts out. The default was also raised from $8 to
$25 on the same evidence.

## Consequences

- The resumed run of that job finished the video in **39 turns for $19.82**,
  reusing the earlier $8.18 of work instead of repeating it.
- A resumed run is a **new session** — it re-reads `SCRIPT.md` and
  `STORYBOARD.md` to orient itself. That costs tokens but keeps resumption
  independent of what was still in context.
- Resume is prompt-level, not session-level: it does not replay the previous
  conversation.
- If the project directory is gone, resume fails fast with a clear message
  rather than silently starting over.

## Alternatives considered

**SDK session resume** via the stored `sessionId`. Tighter continuity, but it
breaks across worker restarts and depends on session storage that the operator
may clear. Filesystem state is the durable thing.
